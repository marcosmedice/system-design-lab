# Algoritmos de Load Balancing

---

Os algoritmos de load balancing definem como as requisições ou conexões são distribuídas entre os servidores disponíveis.

A escolha influencia a distribuição da carga, o aproveitamento dos recursos, a latência e a estabilidade do sistema.

Considere três servidores disponíveis:

```text
             Load Balancer
             /     |     \
            v      v      v
        Server A Server B Server C
```

## Round Robin

Distribui as requisições sequencialmente entre os servidores, seguindo uma ordem circular.

**Exemplo:** com três servidores, cada nova requisição é encaminhada ao próximo servidor.

```text
Requisição 1 → Server A
Requisição 2 → Server B
Requisição 3 → Server C
Requisição 4 → Server A
Requisição 5 → Server B
Requisição 6 → Server C
```

**Vantagens**
- Simples de implementar.
- Distribuição previsível.
- Não exige monitorar a carga de cada servidor para decidir o destino.

**Limitações**
- Não considera a capacidade individual dos servidores.
- Não considera o custo de processamento de cada requisição.
- Pode gerar desequilíbrio quando as requisições têm custos muito diferentes.

**Quando utilizar:** servidores com capacidades semelhantes e requisições com custos relativamente uniformes.

## Weighted Round Robin

É uma variação do Round Robin que atribui um peso a cada servidor. Servidores com pesos maiores recebem proporcionalmente mais requisições.

**Exemplo:** pesos A = 3, B = 2 e C = 1.

```text
Server A: 3 requisições
Server B: 2 requisições
Server C: 1 requisição

Total: 6 requisições
```

A distribuição aproximada será:

- Server A: 50%
- Server B: 33,3%
- Server C: 16,7%

Os pesos podem representar a capacidade relativa dos servidores, embora não garantam que a carga real fique proporcionalmente equilibrada.

**Vantagens**
- Considera diferenças de capacidade.
- Permite distribuir mais tráfego para servidores mais potentes.
- Mantém uma distribuição previsível.

**Limitações**
- Os pesos precisam ser configurados ou ajustados.
- Não considera necessariamente a carga atual.
- Pode ser inadequado quando o custo das requisições varia muito.

**Quando utilizar:** ambientes com servidores de capacidades diferentes.

## Least Connections

Direciona novas conexões ao servidor que possui a menor quantidade de conexões ativas.

```text
Server A: 12 conexões
Server B:  5 conexões  ← destino
Server C:  9 conexões
```

É útil quando as conexões têm durações diferentes, como em aplicações com conexões persistentes.

**Vantagens**
- Considera uma medida da carga atual.
- Pode distribuir melhor conexões de longa duração.
- Adapta-se às variações na quantidade de conexões ativas.

**Limitações**
- Quantidade de conexões não representa necessariamente o uso de CPU ou o custo de processamento.
- Uma conexão pode consumir muito mais recursos que outra.
- Requer acompanhamento das conexões ativas.

**Quando utilizar:** sistemas com conexões de duração variável, como aplicações com WebSocket ou sessões persistentes.

## IP Hash

Utiliza o endereço IP do cliente como entrada para uma função de hash que determina o servidor de destino.

```text
Client A ──┐
           ├──> Hash(IP) ──> Server A
Client B ──┘

Client C ──────> Hash(IP) ──> Server B
```

Enquanto o mapeamento permanecer estável, requisições do mesmo IP tendem a ser direcionadas ao mesmo servidor.

**Vantagens**
- Pode manter afinidade entre cliente e servidor.
- Ajuda em cenários que dependem de sessões armazenadas localmente.
- Não exige armazenar individualmente um mapeamento para cada cliente.

**Limitações**
- Clientes diferentes podem compartilhar o mesmo IP, por exemplo, atrás de um NAT.
- Mudanças no conjunto de servidores podem alterar o destino de muitos clientes.
- A distribuição pode ficar desigual se muitos clientes compartilharem determinados IPs.

**Quando utilizar:** quando existe necessidade de afinidade por IP e as limitações desse mecanismo são aceitáveis.

> Preferencialmente, sessões importantes devem ser armazenadas em um local compartilhado, como Redis ou um banco de dados, para evitar dependência de uma instância específica.

## Consistent Hashing

O Consistent Hashing distribui chaves entre servidores usando um espaço de hash. Quando um servidor é adicionado ou removido, a ideia é minimizar a quantidade de chaves que precisam ser redistribuídas.

Uma representação simplificada é um anel de hash:

```text
                 Hash Ring

             Server A
           /           \
          /             \
    Server C           Server B
          \             /
           \           /
             Chaves
```

Cada chave é mapeada para uma posição no anel e atribuída ao próximo servidor conforme a regra de distribuição.

Diferentemente de um hash convencional baseado diretamente no número de servidores, o Consistent Hashing reduz a quantidade de chaves afetadas quando o conjunto de servidores muda.

**Vantagens**
- Minimiza remapeamentos ao adicionar ou remover servidores.
- Útil para distribuir chaves de cache e dados particionados.
- Pode preservar a afinidade de determinadas chaves com os mesmos servidores.

**Limitações**
- A implementação é mais complexa.
- A distribuição pode ficar desigual sem técnicas como *virtual nodes*.
- Não garante, por si só, equilíbrio de CPU, memória ou número de requisições.

**Quando utilizar:** sistemas distribuídos com particionamento de dados, cache distribuído ou necessidade de manter a associação entre chaves e servidores.

**Observação:** IP Hash e Consistent Hashing são conceitos relacionados, mas não equivalentes. IP Hash usa o IP como chave de afinidade; Consistent Hashing é uma estratégia de distribuição que pode utilizar diferentes tipos de chave.

## Random

Seleciona aleatoriamente um servidor entre os destinos disponíveis.

```text
Requisição 1 → Server C
Requisição 2 → Server A
Requisição 3 → Server A
Requisição 4 → Server B
```

A distribuição tende a se aproximar de uma proporção uniforme com um volume suficientemente grande de requisições independentes, mas não garante equilíbrio em intervalos curtos.

**Vantagens**
- Simples de implementar.
- Não exige manter uma sequência de distribuição.
- Pode funcionar bem em cenários com muitos servidores e requisições.

**Limitações**
- Pode selecionar repetidamente o mesmo servidor em intervalos curtos.
- Não considera a carga atual.
- Não considera diferenças de capacidade, salvo se combinado com mecanismos ponderados.

**Quando utilizar:** sistemas em que uma estratégia simples de distribuição aleatória é suficiente.

---

## Comparação dos algoritmos

| Algoritmo | Critério | Considera carga atual? | Principal aplicação |
|---|---|---|---|
| Round Robin | Ordem sequencial | Não | Servidores semelhantes |
| Weighted Round Robin | Ordem e pesos | Não necessariamente | Capacidades diferentes |
| Least Connections | Conexões ativas | Parcialmente | Conexões persistentes |
| IP Hash | IP do cliente | Não | Afinidade por IP |
| Consistent Hashing | Chave e espaço de hash | Não necessariamente | Cache e particionamento |
| Random | Escolha aleatória | Não | Distribuição simples |

## Como escolher

- **Servidores semelhantes:** Round Robin.
- **Servidores com capacidades diferentes:** Weighted Round Robin.
- **Conexões com durações variadas:** Least Connections.
- **Afinidade baseada no IP:** IP Hash.
- **Cache distribuído ou particionamento de dados:** Consistent Hashing.
- **Simplicidade e distribuição aleatória:** Random.

Nenhum algoritmo é ideal para todos os cenários. A escolha depende do padrão de tráfego, da capacidade dos servidores, da duração das conexões e da necessidade de afinidade.

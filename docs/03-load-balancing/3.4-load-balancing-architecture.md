# Arquiteturas de Load Balancing

---

A arquitetura de load balancing define onde os balanceadores ficam posicionados, como o tráfego é distribuído e como diferentes instâncias, regiões ou infraestruturas participam do atendimento às requisições.

A escolha depende de fatores como volume de tráfego, disponibilidade desejada, distribuição geográfica dos usuários e tolerância a falhas.

## Client → Load Balancer → Servers

É a arquitetura básica de load balancing. Os clientes enviam requisições para um endereço de entrada, e o balanceador distribui o tráfego entre múltiplos servidores.

```text
           Clients
              |
              v
        Load Balancer
         /    |    \
        v     v     v
    Server A B     C
```

### Funcionamento

1. O cliente envia uma requisição ao endereço do serviço.
2. O load balancer seleciona um servidor disponível.
3. O servidor processa a requisição.
4. A resposta retorna ao cliente.

### Vantagens

- Distribuição de carga entre instâncias.
- Escalabilidade horizontal.
- Possibilidade de remover instâncias indisponíveis do tráfego.
- Ponto de entrada único para os clientes.

### Limitações

O balanceador pode se tornar um ponto único de falha se não houver redundância. Além disso, o sistema continua limitado pela capacidade dos servidores e de outras dependências, como bancos de dados.

**Quando utilizar:** aplicações executadas em múltiplas instâncias que precisam distribuir tráfego e escalar horizontalmente.

## Multiple Load Balancers

Uma arquitetura com múltiplos load balancers utiliza balanceadores redundantes para reduzir o risco de indisponibilidade do ponto de entrada.

Uma possibilidade é utilizar um balanceador externo que distribui o tráfego entre balanceadores internos.

```text
                 Clients
                    |
                    v
             External LB
               /      \
              v        v
          Internal LB  Internal LB
              |        |
          +---+---+  +-+-----+
          |   |   |  | |     |
          v   v   v  v v     v
         App App App App App App
```

Outra possibilidade é manter balanceadores redundantes com um mecanismo de endereço virtual ou failover, de modo que um assuma quando o outro falhar.

### Vantagens

- Maior tolerância a falhas.
- Separação entre balanceamento externo e interno.
- Possibilidade de distribuir tráfego entre diferentes grupos de servidores.
- Flexibilidade para escalar diferentes camadas.

### Limitações

- Maior complexidade operacional.
- Mais componentes para monitorar e manter.
- Necessidade de coordenar health checks, roteamento e failover.
- Um balanceador externo ainda pode ser um ponto único de falha se não for redundante.

**Quando utilizar:** sistemas críticos, arquiteturas com múltiplas camadas ou ambientes em que a disponibilidade do próprio balanceador precisa ser protegida.

## Global Load Balancing

Global load balancing distribui o tráfego entre diferentes regiões ou data centers, em vez de se limitar a servidores dentro de uma única região.

A decisão pode considerar disponibilidade regional, latência, capacidade e políticas de distribuição.

```text
                    Clients
                       |
                       v
              Global Load Balancer
                 /             \
                v               v
          Region A          Region B
          Load Balancer     Load Balancer
             /   \             /   \
            v     v           v     v
          App A  App B       App C  App D
```

### Funcionamento

O balanceador global seleciona uma região de destino. Dentro dela, um balanceador regional distribui o tráfego entre as instâncias locais.

### Estratégias possíveis

- Direcionar usuários para a região com menor latência estimada.
- Preferir uma região principal e utilizar outra como contingência.
- Distribuir tráfego entre regiões ativas.
- Remover regiões indisponíveis do roteamento.

### Vantagens

- Redução potencial da latência para usuários distantes.
- Tolerância a falhas regionais.
- Possibilidade de distribuir a capacidade entre regiões.
- Suporte a estratégias de recuperação de desastres.

### Limitações

- Custos e complexidade maiores.
- Necessidade de considerar replicação e consistência dos dados.
- Possíveis diferenças de capacidade entre regiões.
- Failover pode ser afetado pelo tempo de detecção e convergência.
- Uma região alternativa pode não ter capacidade para absorver todo o tráfego.

**Quando utilizar:** aplicações globais ou sistemas que precisam continuar operando mesmo diante da indisponibilidade de uma região inteira.

## DNS Load Balancing

DNS load balancing utiliza respostas DNS para direcionar clientes a diferentes endereços IP associados a um serviço.

O DNS pode retornar múltiplos endereços ou selecionar respostas conforme políticas de distribuição, localização ou saúde dos destinos.

```text
             Client
                |
                v
          DNS Resolver
                |
                v
       DNS Load Balancing
          /          \
         v            v
      Server A     Server B
       IP: A         IP: B
```

Por exemplo, um domínio pode resolver para diferentes endereços de servidores ou balanceadores, conforme a política configurada.

### Estratégias comuns

- Retornar múltiplos endereços IP.
- Alternar a ordem dos endereços retornados.
- Selecionar destinos por região.
- Deixar de retornar endereços considerados indisponíveis, quando o serviço oferece health checks integrados.

### Vantagens

- Distribuição de tráfego sem exigir um balanceador HTTP central para todas as decisões.
- Integração com roteamento global.
- Possibilidade de direcionar clientes para diferentes regiões.
- Simplicidade conceitual.

### Limitações

- O DNS não controla diretamente cada requisição HTTP.
- Respostas podem ficar em cache conforme o TTL.
- A alteração de uma resposta não afeta imediatamente todos os clientes.
- Resolvers e clientes podem tratar respostas de maneiras diferentes.
- O DNS, isoladamente, não garante que o destino escolhido esteja saudável.

**Quando utilizar:** distribuição inicial de tráfego entre endereços ou regiões, especialmente quando combinada com serviços de DNS gerenciado e health checks.

## Geographic Routing

Geographic routing direciona clientes para destinos com base em sua localização geográfica ou região de origem.

É frequentemente implementado por serviços de DNS global, balanceadores globais ou redes de distribuição de conteúdo.

```text
               Clients
                  |
          +-------+-------+
          |       |       |
          v       v       v
        Brazil   Europe   Asia
          |       |       |
          v       v       v
       Region A Region B Region C
```

### Funcionamento

1. O sistema estima a localização do cliente, normalmente a partir do IP ou de informações do resolvedor DNS.
2. Uma política determina a região de destino.
3. O cliente é direcionado à infraestrutura correspondente.

### Vantagens

- Pode reduzir a latência.
- Permite manter tráfego próximo dos usuários.
- Ajuda a atender requisitos regionais de operação ou residência de dados, quando combinado com controles adequados.
- Permite aplicar políticas específicas por região.

### Limitações

- A localização estimada por IP nem sempre representa a localização real do usuário.
- VPNs, proxies e resolvedores DNS podem afetar a decisão.
- A região geograficamente mais próxima não é necessariamente a mais rápida ou disponível.
- Pode haver desequilíbrio de carga se uma região receber muito mais tráfego que as outras.

**Quando utilizar:** aplicações com usuários distribuídos geograficamente ou requisitos específicos de latência e roteamento regional.

---

## Comparação das arquiteturas

| Arquitetura | Escopo | Principal objetivo |
|---|---|---|
| Client → LB → Servers | Uma camada de aplicação | Distribuir tráfego entre instâncias |
| Multiple Load Balancers | Múltiplos balanceadores | Redundância e separação de camadas |
| Global Load Balancing | Múltiplas regiões | Disponibilidade e distribuição global |
| DNS Load Balancing | Resolução de nomes | Direcionar clientes entre destinos |
| Geographic Routing | Diferentes localidades | Encaminhar tráfego conforme a região |

## Como escolher

- **Aplicação com várias instâncias em uma região:** load balancer regional.
- **Balanceador como possível ponto único de falha:** balanceadores redundantes.
- **Usuários em diferentes continentes ou necessidade de recuperação regional:** global load balancing.
- **Distribuição de endereços ou regiões via DNS:** DNS load balancing.
- **Políticas de roteamento baseadas na localização:** geographic routing.

Essas estratégias podem ser combinadas. Por exemplo, DNS com roteamento geográfico pode direcionar o cliente a uma região, enquanto um load balancer regional distribui as requisições entre as instâncias dessa região.

```text
                  Client
                     |
                     v
            DNS / Global Routing
                     |
             +-------+-------+
             |               |
             v               v
          Region A        Region B
             |               |
             v               v
        Regional LB     Regional LB
             |               |
          +--+--+          +--+--+
          v     v          v     v
        App A App B      App C App D
```

A decisão arquitetural deve considerar não apenas a distribuição do tráfego, mas também a capacidade disponível, a detecção de falhas, o comportamento do DNS, a consistência dos dados e a recuperação após uma interrupção.

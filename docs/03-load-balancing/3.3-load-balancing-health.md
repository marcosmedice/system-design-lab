# Health Checks e Disponibilidade

---

Em arquiteturas com múltiplas instâncias, não basta distribuir requisições entre servidores: é necessário identificar quais instâncias estão aptas a receber tráfego e como reagir quando uma falha ocorre.

Esses mecanismos ajudam a manter a disponibilidade do sistema e a evitar que requisições sejam encaminhadas para instâncias indisponíveis ou em processo de encerramento.

## Health Check

Um **health check** é uma verificação periódica que avalia se um servidor ou serviço está funcionando de forma adequada.

O load balancer pode utilizar o resultado para decidir se uma instância deve continuar recebendo tráfego.

```text
             Load Balancer
              /         \
             v           v
         Server A     Server B
             |           |
          Healthy      Unhealthy
             |           |
             v           X
        Recebe tráfego  Removido
```

As verificações podem avaliar:
- Se a aplicação responde.
- Se uma porta está aceitando conexões.
- Se um endpoint HTTP retorna o resultado esperado.
- Se dependências críticas estão acessíveis, quando essa verificação faz parte do critério de saúde.

### Tipos de verificação

- **Passive health check:** identifica problemas a partir de falhas observadas durante o tráfego real.
- **Active health check:** envia verificações periódicas para avaliar a disponibilidade do destino.

Uma verificação excessivamente simples pode considerar saudável uma aplicação que responde HTTP, mas não consegue executar operações importantes. Por outro lado, verificar todas as dependências em cada health check pode causar remoções desnecessárias quando uma dependência compartilhada falha.

A verificação deve refletir o objetivo operacional do componente.

## Readiness

Readiness indica se uma instância está **pronta para receber requisições**.

Uma aplicação pode estar em execução, mas ainda não estar preparada para atender tráfego, por exemplo, enquanto inicializa configurações ou estabelece conexões necessárias.

```text
Aplicação inicia
       |
       v
Inicializando
       |
       v
Readiness = false
       |
       v
Inicialização concluída
       |
       v
Readiness = true
       |
       v
Recebe tráfego
```

Se uma instância deixar de estar pronta, o sistema de orquestração ou balanceamento pode parar de encaminhar novas requisições para ela.

**Uso principal:** controlar a entrada e a permanência de instâncias no conjunto de destinos aptos a receber tráfego.

## Liveness

Liveness indica se a aplicação continua funcionando ou se entrou em um estado em que precisa ser reiniciada.

Uma aplicação pode estar em execução, mas travada ou incapaz de progredir.

```text
Aplicação em execução
         |
         v
Verificação de liveness
         |
     +---+---+
     |       |
   Saudável  Falha
     |       |
     v       v
 Continua  Reinício
```

Em ambientes como Kubernetes, uma falha persistente na liveness probe pode levar ao reinício do contêiner.

### Readiness vs Liveness

| Característica | Readiness | Liveness |
|---|---|---|
| Pergunta | Pode receber tráfego? | Continua funcionando? |
| Falha típica | Dependências ainda não prontas | Aplicação travada |
| Ação comum | Remover temporariamente do tráfego | Reiniciar a aplicação |
| A aplicação precisa ser reiniciada? | Não necessariamente | Pode ser necessário |

**Importante:** readiness e liveness não são sinônimos. Uma aplicação pode estar viva, mas não pronta para receber tráfego.

Uma configuração inadequada de liveness pode provocar reinícios em cascata. Por exemplo, reiniciar todas as instâncias porque um banco de dados compartilhado está temporariamente indisponível pode piorar a recuperação.

## Failover

Failover é a transferência da operação para outro servidor, instância ou componente quando o destino principal falha.

Em um sistema com balanceamento, o failover pode ocorrer quando uma instância deixa de responder e o tráfego passa a ser direcionado às demais instâncias saudáveis.

```text
Antes da falha:

             Load Balancer
              /         \
             v           v
         Server A     Server B
          Healthy      Healthy


Após a falha:

             Load Balancer
              /         \
             X           v
         Server A     Server B
         Unhealthy     Healthy
                         |
                         v
                  Continua atendendo
```

O failover pode ser:
- **Automático:** o sistema detecta a falha e realiza a transição sem intervenção manual.
- **Manual:** um operador executa a mudança.
- **Local:** a operação é transferida para outra instância na mesma infraestrutura.
- **Geográfico:** a operação é transferida para outra região ou localidade.

O failover depende de mecanismos de detecção, destinos alternativos disponíveis e uma estratégia de recuperação.

### Considerações

- O tempo de detecção influencia o tempo de indisponibilidade.
- Conexões existentes podem ser interrompidas.
- Requisições em andamento podem falhar.
- A capacidade restante precisa suportar o tráfego adicional.
- Estado armazenado apenas na instância que falhou pode não estar disponível no destino alternativo.

Failover não garante continuidade transparente. A aplicação e os clientes precisam lidar com falhas, timeouts e possíveis tentativas de repetição.

## Connection Draining

Connection draining é o processo de parar de encaminhar novas conexões ou requisições para uma instância, permitindo que as operações existentes terminem antes de ela ser removida.

É útil durante deploys, escalabilidade e manutenção.

```text
Instância recebe tráfego
          |
          v
Inicia connection draining
          |
          +----> Novas conexões: outro servidor
          |
          +----> Conexões existentes: continuam
                            |
                            v
                    Operações concluídas
                            |
                            v
                    Instância removida
```

O comportamento exato depende do protocolo e da implementação. Em conexões HTTP persistentes, por exemplo, pode ser necessário impedir novas requisições em conexões existentes, aguardar um período de encerramento ou solicitar o fechamento controlado da conexão.

### Benefícios

- Reduz falhas durante deploys.
- Permite encerramento controlado das instâncias.
- Diminui a interrupção de requisições em andamento.
- Facilita a substituição gradual de servidores.

### Limitações

- Conexões de longa duração podem atrasar a remoção.
- É necessário definir um tempo máximo de drenagem.
- Ao atingir esse limite, conexões ainda abertas podem ser encerradas.
- Clientes precisam tolerar desconexões e, quando apropriado, reconectar.

---

## Relação entre os mecanismos

| Mecanismo | Objetivo |
|---|---|
| Health check | Detectar o estado de um destino |
| Readiness | Determinar se pode receber tráfego |
| Liveness | Detectar se a aplicação precisa ser recuperada |
| Failover | Transferir a operação após uma falha |
| Connection draining | Remover uma instância de forma controlada |

Esses mecanismos são complementares. Health checks ajudam a identificar o estado das instâncias; readiness controla sua participação no tráfego; liveness auxilia na recuperação; failover direciona a operação para alternativas; e connection draining permite remoções planejadas com menor interrupção.

# Requisitos de um Sistema

---

## Requisitos Funcionais e Requisitos Não Funcionais

### Functional Requirements

Requisitos funcionais definem as ações que um sistema deve ser capaz de executar, o que usuários ou outros sistemas conseguem fazer, ex:

Para uma plataforma de vídeo:

- Upload
- Reproduzir
- Pesquisar
- Comentar
- Criar playlists

etc.

### Non-Functional Requirements

Requisitos nâo funcionais descrevem as condições que os requisitos funcionais devem operar, capacidade do sistema, ex:

- Latência
- Vazão/Taxa de transferência (Throughput)
- Disponibilidade
- Durabilidade
- Consistência
- Segurança
- Recuperabilidade
- Operabilidade
- Custos

---

## Availability

> Disponibilidade mede o percentual de tempo que um sistema se mantém operacional e acessível. Típicamente definido em "nines" (99,9% = three nines), traduz diretamente a experiência do usuário e o impacto no negócio.

- Three nines (99,9%) permite 8,76 horas de indisponibilidade por ano.
- Five nines (99,999%) permite somente 5,26 minutos de indisponibilidade por ano.

> Não é somente "uptime", o sistema deve conseguir responder os requests corretamente, não apenas responder com mensagens de erro. A alta disponibilidade exige redundância (redundancy), detecção de falhas (fault detection) e degradação graciosa (graceful degradation).

### Redundancy

> Todo componente crítico deve ter uma capacidade de backup para lidar com falhas.

- Servidores de aplicações ficam por trás de Load Balancers que desviam o tráfego de instâncias com falhas.
- Bancos de dados usam replicações dos dados para fornecer réplicas.
- Redes usam switches e roteadores redundantes.
- Sistemas de armazenamento mantém múltiplas cópias dos dados em diferentes domínios.

### Fault detection/Health checking

> Determinam quão rápido um sistema reconhece e responde à falhas. 
> 
> Health checks passivos monitoram as taxas de sucesso dos requests e timeouts, removendo backends quando a taxa de erros excede o limite estabelecido.
> 
> Health checks ativos verificam periodicamente os endpoints, testando as funcionalidades, não somente a conectividade.

Os trade-offs estão entre a velocidade de detecção e a ocorrência de falsos positivos:

- Regras de timeouts agressivos detectam falhas rapidamente, mas acarretam o risco de falhas em cascata quando pequenas instabilidades na rede desencadeiam uma avalanche de tentativas de reexecução.
- Regras de timeout conservadores toleram problemas transitórios, mas permitem que as falhas aferem os usuários por mais tempo

### Graceful degradation

> Reconhece que a funcionalidade parcial é preferível à falha total. Exige projetar serviços com sistemas com baixo acoplamento, onde as falhas são isopladas e componentes não críticos podem falhar sem comprometer a funcionalidade principal.
> 
> Mecanismos de circuit breaker evitam falhas em cascata ao interromper as requiisições para dependências que estão falhando, permitindo que elas tenham tempo para recuperar.

## Scalability

> Capacidade de um sistema de lidar com aumento de carga aumentando os recursos.

### Vertical scaling (scaling up)

> Adicionar mais potência às máquinas existentes:
> - CPU's mais rápidas
> - Mais memória RAM
> - Mais capacidade de disco
> 
> PRÓS:
> - Abordagem mais simples, mantém a arquitetura. 
> - Funciona bem para bancos de dados que se beneficiam da consistência em uma única máquina (PostgreSQL e MySQL) (porém torna-se uma limitação).
>
> CONTRAS:
> - O hardware físico possui limites máximos.
> - Os custos crescem de forma não linear.
> - Não oferece redundância, a falha de uma máquina compromete todo o serviço.

### Horizontal scaling (scaling out)

> Distribuição da carga por múltiplas máquinas. Em teoria permite capacidade ilimitada, basta adicionar mais nós.
> 
> Infraestruturas de cloud modernas oferecem escalabilidade horizontal economicamente atrativa.
> 
> Escalabilidade horizontal introduz complexidade inerente aos sistemas distribuídos: particionamento de dados, load balancers e coordenação do estado entre as máquinas.

## Reliability (confiança)

> Capacidade de um sistema continuar trabalhando corretamente mesmo que tenha falhas (problemas de hardware, rede, bugs)
> 
> O sistema pode ser confiado que vai operar corretamente em diferentes condições.
> 
> Sistemas confiáveis devem:
> - Continuar operando mesmo que com falhas de software ou hardware.
> - Se recuperar automaticamente de interrupções
> - Suportar aumento de tráfego inesperado
> - Proteger os dados de perdas
> - Detectar problemas rapidamente
> - Degradar gacriosamente ao invés de falhar completamente

Formas de se medir:
- Uptime percentage
- Mean time between failures (MTBF)
- Mean time to repair (MTTR)
- Error rate

---

## Durability

> Garantia de que, uma vez salvos, os dados ficam firmemente preservados mesmo com falhas e interrupções.
> 
> Especialmente importante em bancos de dados e sistemas de armazenamento.

---

## Consistency

> Consistência é a garantia de que os dados observados por diferentes partes de um sistema seguem as regras de atualização definidas pelo sistema, evitando que usuários ou componentes tenham visões incompatíveis dos dados.

Em sistemas distribuídos, diferentes níveis de consistência podem ser utilizados dependendo dos requisitos:

- Strong consistency: após uma escrita ser confirmada, todas as leituras posteriores observam o novo valor.
- Eventual consistency: diferentes réplicas podem apresentar valores diferentes temporariamente, mas convergem para o mesmo estado.
- Causal consistency: operações relacionadas causalmente são observadas na mesma ordem por todos os participantes.

A consistência normalmente envolve trade-offs com disponibilidade, latência e particionamento de rede.

---

## Latency

> Latência é o tempo necessário para uma operação ser concluída, normalmente medido desde o envio de uma requisição até o recebimento de sua resposta.

Pode ser medida em diferentes percentis:

- P50 (mediana): representa uma requisição típica.
- P95: 95% das requisições terminam dentro desse tempo.
- P99: 99% das requisições terminam dentro desse tempo.

A latência de um sistema pode ser reduzida através de:

- Caching
- Redução de chamadas entre serviços
- Processamento paralelo
- Proximidade geográfica entre componentes
- Otimização de queries
- Connection pooling
- Asynchronous processing

---

## Throughput

> Throughput é a quantidade de trabalho que um sistema consegue processar em determinado período de tempo.

Pode ser medido em:

- Requests per second (RPS)
- Queries per second (QPS)
- Mensagens por segundo
- Transações por segundo (TPS)
- MB/s ou GB/s

O throughput máximo de um sistema é limitado pelo seu gargalo (bottleneck).

Para aumentar o throughput, podem ser utilizadas técnicas como:

- Horizontal scaling
- Processamento paralelo
- Batching
- Caching
- Particionamento
- Processamento assíncrono

---

## Maintainability

> Maintainability é a facilidade com que um sistema pode ser compreendido, modificado, testado e corrigido ao longo do tempo, sem introduzir problemas excessivos.

Um sistema maintainable normalmente possui:

- Código modular e baixo acoplamento
- Interfaces bem definidas
- Testes automatizados
- Documentação adequada
- Observabilidade
- Deploy e rollback seguros
- Código consistente e compreensível

A maintainability reduz o custo e o risco de evoluir o sistema conforme novos requisitos surgem.

---

## Fault tolerance

> Fault tolerance é a capacidade de um sistema continuar fornecendo suas funções, total ou parcialmente, mesmo quando componentes individuais apresentam falhas.

Enquanto reliability é uma propriedade mais ampla do sistema, fault tolerance é uma das formas utilizadas para alcançá-la.

Principais técnicas:

- Redundancy
- Replication
- Failover
- Health checks
- Timeouts
- Retries
- Circuit breakers
- Graceful degradation
- Isolation

O objetivo é impedir que uma falha localizada cause a indisponibilidade do sistema inteiro.

---

## Disaster recovery

> Disaster recovery (DR) é o conjunto de estratégias e procedimentos utilizados para restaurar sistemas e dados após um desastre que comprometa significativamente sua operação.

Exemplos de desastres:

- Falha de uma região inteira
- Perda de infraestrutura
- Corrupção ou exclusão de dados
- Ransomware
- Erros humanos graves
- Desastres naturais

Principais mecanismos:

- Backups
- Replicação entre regiões
- Snapshots
- Redundância geográfica
- Failover
- Infraestrutura reproduzível
- Procedimentos de recuperação

Dois indicadores importantes:

- **RTO (Recovery Time Objective):** tempo máximo aceitável para restaurar o serviço.
- **RPO (Recovery Point Objective):** quantidade máxima de dados que pode ser perdida, medida em tempo.

Exemplo:

> RTO de 1 hora → o sistema deve voltar a operar em até 1 hora.
>
> RPO de 15 minutos → em um desastre, pode-se perder no máximo 15 minutos de dados.

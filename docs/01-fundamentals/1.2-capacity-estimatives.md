# Capacidade e estimativas

---

## Requests per second — RPS

> RPS (Requests per Second) representa a quantidade de requisições HTTP ou operações recebidas por um sistema a cada segundo.

É utilizado para estimar a carga que uma aplicação precisa suportar.

Exemplo:

* 10.000 requests em 10 segundos
* RPS médio = 1.000

É importante considerar tanto o RPS médio quanto o RPS de pico.

---

## Queries per second — QPS

> QPS (Queries per Second) representa a quantidade de consultas executadas por segundo em um sistema, normalmente utilizado para medir a carga sobre bancos de dados ou mecanismos de busca.

Exemplo:

* Uma aplicação recebe 1.000 RPS.
* Cada request executa em média 3 queries no banco.
* QPS aproximado = 3.000.

Um único request pode gerar várias queries.

---

## Concurrent users

> Concurrent users representa a quantidade de usuários que estão realizando operações ou mantendo uma interação ativa com o sistema simultaneamente.

Não deve ser confundido com usuários totais ou RPS.

A quantidade de usuários concorrentes depende principalmente da taxa de chegada de requisições e do tempo que cada operação permanece ativa.

Uma aproximação pode ser obtida pela **Lei de Little**:

```text
Concurrent users ≈ RPS × duração média da operação
```

---

## Peak traffic

> Peak traffic representa a maior carga de tráfego esperada em determinado período.

É utilizado para dimensionar a capacidade necessária para suportar períodos de maior demanda.

Exemplos:

* Black Friday
* Horário de pico
* Lançamento de um produto
* Evento de grande audiência

O sistema normalmente deve ser dimensionado considerando o pico, e não somente a média.

---

## Average traffic

> Average traffic representa a carga média de tráfego durante determinado período.

Pode ser calculado a partir do número total de operações dividido pelo período observado.

```text
Average RPS = total de requests / duração do período
```

A média é útil para estimar consumo e custos, mas não representa necessariamente a capacidade necessária para lidar com picos.

---

## Storage estimation

> Storage estimation é a estimativa da quantidade de armazenamento necessária para armazenar os dados produzidos pelo sistema durante determinado período.

Deve considerar:

* Quantidade de registros
* Tamanho médio dos registros
* Dados históricos
* Índices
* Metadados
* Réplicas
* Backups
* Crescimento futuro

Uma estimativa básica:

```text
Storage = quantidade de registros × tamanho médio do registro
```

---

## Bandwidth estimation

> Bandwidth estimation é a estimativa da quantidade de dados que precisa ser transferida pela rede durante determinado período.

Pode ser estimada considerando:

* Número de requests
* Tamanho médio das requisições
* Tamanho médio das respostas
* Tráfego de entrada (ingress)
* Tráfego de saída (egress)

Uma aproximação:

```text
Bandwidth ≈ requests/sec × tamanho médio dos dados
```

Normalmente expressa em **bits/s**, como Mbps ou Gbps.

---

## Read/write ratio

> Read/write ratio representa a proporção entre operações de leitura e operações de escrita realizadas por um sistema.

Exemplo:

```text
100 operações
├── 80 reads
└── 20 writes

Read/Write ratio = 4:1
```

Essa relação influencia decisões de arquitetura, como caching, replicação, escolha de banco de dados e dimensionamento de infraestrutura.

---

## Data growth

> Data growth representa a velocidade com que a quantidade de dados armazenados por um sistema aumenta ao longo do tempo.

Pode ser medido em:

* GB/dia
* TB/mês
* Registros/dia
* Crescimento percentual

A estimativa deve considerar tanto o crescimento atual quanto projeções futuras para determinar capacidade de armazenamento e estratégias de retenção, arquivamento e particionamento.

---

## Back-of-the-envelope calculations

> Back-of-the-envelope calculations são estimativas rápidas utilizadas para determinar a ordem de grandeza dos recursos necessários para um sistema, utilizando hipóteses e cálculos simples em vez de dados exatos.

Normalmente estimam:

* RPS/QPS
* Storage
* Bandwidth
* Número de servidores
* Capacidade de processamento
* Crescimento de dados

O objetivo não é obter um número exato, mas verificar se uma arquitetura é **tecnicamente e economicamente plausível**.

Exemplo:

```text
10 milhões de usuários
× 10 requests/dia
= 100 milhões requests/dia

100.000.000 / 86.400
≈ 1.157 RPS médio
```

Depois, fatores de pico podem ser aplicados para estimar o RPS máximo.

---

## Latency budgets

> Latency budget é o tempo máximo disponível para que uma operação completa seja executada, distribuído entre os diferentes componentes envolvidos no processamento da requisição.

Exemplo:

```text
Total: 500 ms

API Gateway       → 20 ms
Application       → 100 ms
Database          → 150 ms
External API      → 180 ms
Network/overhead  → 50 ms
                    -----
                    500 ms
```

O orçamento permite identificar quais componentes possuem maior impacto na latência total e estabelecer limites para cada etapa.

Em sistemas distribuídos, o orçamento precisa considerar também chamadas sequenciais, paralelas e dependências externas.
